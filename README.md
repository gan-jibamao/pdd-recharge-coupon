# 拼多多「领 30 元话费券」自动领取

Surge cron 脚本。每天零点低频单发领券，顺带维护连续打卡。

**不依赖签名**：真机抓包证明该接口只靠 Cookie 鉴权，请求体里没有 `anti_content`，也没有 `AccessToken` 头。

## 它做什么

| 时间 | 动作 |
|---|---|
| 23:59:50 | 停止一切请求，静默 |
| 00:00:01.05 | 单发一次 `gain/award` |
| 命中 | 补一枪签到（领券后周期归零），通知成功 |
| 被限流 | 00:00:16、00:01:01 各补一枪，当日窗口封顶 3 发 |
| 00:02 | 补枪班次（券池是分钟级寿命） |
| 12:00 | 白天补签，防连续打卡断裂 |

## 为什么是「低频」而不是「高频抢」

2026-11-10 零点窗口的完整抓包推翻了很多想当然的假设：

| 时刻 | 事实 |
|---|---|
| 00:00:01 | 3 条 `gain/award` 同秒并发 → 全部 `4000004` |
| 00:00:02–07 | 每秒 1 发，仍全部 `4000004` |
| 00:00:26 | 券池才消耗 **21%**（距归零还有很久） |
| 00:00:27 | 第 11 发，依旧 `4000004` |
| 00:07:35 | 单发 → `6071002`（业务层响应，**限流已解除**） |
| 00:04 | 券池 100%，当日结束 |

三条结论直接决定了实现：

1. **限流按次数累计**，不是按秒重置。11 发挤在 26 秒里，封锁持续到 7 分钟后才恢复。
2. **券池寿命是分钟级**，不是秒级。所谓「窗口只有 10 秒」是错的。
3. **`6071002` 是售罄终态**，不是「火爆可重试」。分错类会对一个死掉的池子连打十几发。

所以策略是：**少打、拉开、打准**。当日每窗口 3 发，全网一天最多 9 发。

## 安装

### 1. 托管脚本

把 `scripts/` 下两个文件放到 Surge 能取到的地方，或直接粘贴进 Surge 的本地脚本编辑器。

> 本地脚本不会自动更新。改了内容必须重新粘贴，否则永远跑旧版。

### 2. 合并配置

参考 `conf/Surge.snippet.conf`，把 `[Script]` 段并进现有配置。

`conf/MITM.conf.example` 是需要的 MITM 域名，不含任何证书。

### 3. 采一次 Cookie

打开拼多多 → 进「充值中心 → 领 30 元话费券」页面 → 停留十几秒。

`pdd-cookie-capture.js` 会自动把登录态写进 `$persistentStore`，并弹一条「Cookie 已更新」。

前提：MITM 已开、证书已安装并信任。

## 验证

Surge 日志里应出现：

```
[PDD券] 开始执行（v19），日期 2026-11-XX
[PDD券] 连续打卡 5 天 / 需 5 天；可领券=false；可签到=false；状态=31
```

看到 `v18` 就是没粘贴成功。确认版本号是唯一可靠的检查手段。

## 错误码

| code | 含义 | 脚本行为 |
|---|---|---|
| `6071002` / `6070006` | 券已发完 | 立即停手，不重试 |
| `4000004` | 请求频率超限 | 退避 15s / 45s |
| `6070004` | 今日已签到 | 视为已落地 |
| `40001` | 登录态 / 风控拒绝 | 停手并通知 |

完整契约见 [docs/PROTOCOL.md](docs/PROTOCOL.md)。

## 已知限制

- **Cookie 会过期**。失效后需重新打开 App 让采集脚本刷新。
- **只支持 iOS + Surge**。逻辑本身可移植，但依赖 Surge 的 `$httpClient` / `$persistentStore` / cron。
- **未在跨版本客户端上验证**。接口字段取自 8.30.0 抓包。
- **额度是平台控制的**。脚本只能减少无谓的限流损耗，不能提高平台放券量。
